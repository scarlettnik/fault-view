# Структура FaultView

## Решение

FaultView хранится в одном Git-репозитории с тремя изолированными приложениями.
Корень репозитория — каталог `FaultView/`; единственный `.git/` находится здесь.
История, ветки и адрес `origin` сохранены. Лендинг перенесён в `apps/landing/`.

| Каталог         | Ответственность                     | Зависимости и настройки                        |
| --------------- | ----------------------------------- | ---------------------------------------------- |
| `apps/landing`  | Публичный статический сайт и демо   | Собственные `package.json`, lock-файл, линтеры |
| `apps/frontend` | Пользовательский интерфейс продукта | Будут добавлены вместе с приложением           |
| `apps/backend`  | API, данные и серверная логика      | Будут добавлены вместе с сервисом              |
| `docs`          | Общие решения и инструкции          | Не участвует в сборке сайта                    |

Корневой `package.json` содержит только короткие команды для работы из корня.
Общего `node_modules`, npm workspaces и общего lock-файла нет. Это позволяет
добавить backend на другом языке и менять frontend без обновления инструментов
лендинга. Каждая часть должна устанавливаться и проверяться из своего каталога.

## Границы

- Лендинг остаётся самостоятельным сайтом с демонстрационными данными.
  Для его просмотра и публикации API не нужен.
- Frontend взаимодействует с backend через документированный HTTP API.
  Исходники одного приложения не импортируют файлы другого через `../`.
- Контракт API хранится в `docs/`, когда он появится. Общий пакет добавляется
  только при появлении реальной потребности, с явным списком потребителей.
- Секреты принадлежат конкретному сервису и хранятся локально или в окружении
  хостинга. `.env.example` содержит только безопасные примеры.
- Внешние URL приложения и API задаются явно в конфигурации соответствующей части,
  а не относительными файловыми путями к соседним приложениям.

## Ручные изменения

| Что нужно изменить                | Где редактировать                    | Как проверить                              |
| --------------------------------- | ------------------------------------ | ------------------------------------------ |
| Тексты и разметку сайта           | `apps/landing/index.html`            | `npm run check:landing`, открыть страницу  |
| Стили сайта                       | `apps/landing/styles/`               | `npm run check:landing`, открыть страницу  |
| Демонстрации и поведение лендинга | `apps/landing/scripts/`              | `npm run check:landing`, пройти сценарий   |
| Иконки и другие ресурсы сайта     | `apps/landing/assets/`               | `npm run build:landing`, открыть страницу  |
| Правила линтеров лендинга         | Конфигурации внутри `apps/landing/`  | `npm run check:landing`                    |
| Публикуемые каталоги лендинга     | `apps/landing/tooling/build.mjs`     | `npm run build:landing`, проверить `dist/` |
| Публикацию и условия запуска      | `.github/workflows/pages.yml`        | Проверить PR и затем Pages после merge     |
| Будущий UI или API                | `apps/frontend/` или `apps/backend/` | Команды конкретного приложения             |

HTML использует относительные пути к соседним `styles/`, `scripts/` и `assets/`.
Поэтому перенос каталога сохраняет загрузку ресурсов, включая Pages по пути
`/fault-view/`. При добавлении публичных файлов вне этих каталогов расширьте
список в `tooling/build.mjs`; копировать весь монорепозиторий в Pages нельзя.

## Сборка и CI

`npm run build:landing` заново создаёт `apps/landing/dist/` и копирует в него
`index.html`, `styles/`, `scripts/`, `assets/`, а также создаёт `.nojekyll`.
Зависимости, README, конфигурации и другие приложения в артефакт не попадают.

Проверки и публикация разделены на два jobs. Проверки не используют GitHub
Environment. Только публикация из `main` использует окружение `github-pages`.
Workflow ограничен путями лендинга, собственным YAML и корневыми npm-командами.
При добавлении CI frontend/backend создавайте отдельные workflows с их путями
и собственными зависимостями.

## Проверка результата миграции

Миграция считается успешной, когда лендинг устанавливается и проверяется из
`apps/landing/`, сборка содержит только публичные файлы, а PR не создаёт деплой.
После слияния в `main` существующий адрес Pages должен открывать тот же сайт.
Проверка этих условий не требует выбора стека frontend/backend.
