# Публикация лендинга

## Единственный канал публикации

Лендинг публикуется через GitHub Actions → GitHub Pages. Workflow находится
в `.github/workflows/pages.yml` в корне репозитория. Его jobs:

1. `check` устанавливает зависимости только `apps/landing/`, проверяет
   форматирование и линтеры, собирает `apps/landing/dist/`.
2. `deploy` публикует готовый артефакт после успешного `check`, только из `main`.

Разделение сборки и публикации соответствует
[инструкции GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).
Право записи в Pages и OIDC есть только у job публикации.

| Событие                                             | Проверки | Деплой |
| --------------------------------------------------- | -------- | ------ |
| Push в `main` с изменениями лендинга                | Да       | Да     |
| PR с изменениями лендинга                           | Да       | Нет    |
| Изменения только `apps/frontend` или `apps/backend` | Нет      | Нет    |
| Изменения только общей документации                 | Нет      | Нет    |
| Ручной запуск workflow из `main`                    | Да       | Да     |
| Ручной запуск из другой ветки                       | Да       | Нет    |

Изменение самого workflow или корневого `package.json` также запускает проверку
и, для push в `main`, публикацию. Старый workflow заменён в том же файле, поэтому
в репозитории нет второго параллельного механизма деплоя.

## Переход на новую структуру

1. Сначала проверьте PR с новой структурой. Проверки должны пройти без окружения
   `checks` и без публикации ветки.
2. В GitHub откройте **Settings → Pages → Build and deployment**. Источником
   должен быть **GitHub Actions**. Если он уже выбран, менять его не нужно.
3. Слейте ветку в `main`. Перенос в `apps/landing/` запустит новый workflow.
4. Убедитесь, что `Publish landing` завершился успешно, и откройте URL из job.
   Проверьте загрузку CSS, JS, favicon и работу демонстрации.

Имя репозитория и домен не меняются; `apps/landing` не добавляется к публичному
URL. На Pages загружается содержимое `dist/`, в корне которого лежит `index.html`.

## Лишние окружения и старые записи

Старый workflow привязывал проверки PR к окружению `checks`, создавая лишние
записи deployments. Новый job проверки не содержит `environment`; единственное
окружение публикации — `github-pages`.

Изменение YAML не удаляет прежние записи и настройки на стороне GitHub.
После перехода старое окружение `checks` можно удалить в
**Settings → Environments**, предварительно убедившись, что его не использует
другой workflow. `github-pages` нужно сохранить. Историю состоявшихся публикаций
можно оставить: она не запускает новые деплои.

## Повтор публикации и откат

В **Actions → Landing checks and Pages → Run workflow** выберите `main`.
Сайт пройдёт те же проверки и будет опубликован повторно.

Для отката исправьте или отмените проблемный коммит через `git revert` в отдельной
ветке и слейте PR в `main`. Ручной запуск workflow из старой ветки не публикует
её содержимое: публикация разрешена только для `main`.

## Проверка без GitHub

Из корня `FaultView/`:

```sh
npm run setup:landing
npm run check:landing
npm run build:landing
python3 -m http.server 4173 --bind 127.0.0.1 --directory apps/landing/dist
```

Откройте <http://127.0.0.1:4173>. Локальная проверка подтверждает содержимое
артефакта; разрешения GitHub, правила окружения и фактическую публикацию нужно
проверить по результату Actions после слияния.
