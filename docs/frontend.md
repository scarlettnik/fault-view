# Frontend MVP: границы и проверка

## Поток данных

UI вызывает типизированный Redux dispatch → createAsyncThunk выполняет локальную операцию → workspace slice обновляет проект → подписка store сохраняет состояние в localStorage → типизированный selector обновляет UI. Серверная синхронизация и RTK Query в этой версии не используются.

Локальная асинхронность нужна для демонстрации загрузки, прогресса и отмены. Все учебные результаты воспроизводимы; случайный выбор PASS/FAIL не используется. Ошибка файла возникает на настоящем локальном разборе спецификации.

## Проверяемые границы

| Граница             | Проверка                                                                              |
| ------------------- | ------------------------------------------------------------------------------------- |
| Ввод проекта        | Валидация имени, URL, лимита, размера и содержимого OpenAPI                           |
| Разбор спецификации | JSON/YAML, операция без responses, внешние ссылки, локальные operationId/operationRef |
| Граф и план         | Два направления, циклы, исключения, дедупликация, пустой план и предел 100            |
| Redux               | Сохранение/удаление, история, pending/fulfilled/rejected, отмена и освобождение busy  |
| Хранилище           | Перезагрузка, ошибки записи и повреждённое содержимое без автоматической перезаписи   |
| UI                  | Форма, клавиатура графа, готовые компоненты, адаптивная навигация                     |
| Полный сценарий     | CRUD и localStorage; граф → план → симуляция → история; без запросов к API            |

Матрица результатов предшествует подробностям; первая комбинация выбрана автоматически. В текущей версии вместо настоящего скриншота внешнего приложения отображается DOM-предпросмотр локального сценария.

## Локальные команды и CI

Основной режим автоматизации — **local-CI parity**: `npm run verify` использует те же команды, что quality job. Pre-commit вызывает только `npm run check` без E2E и Storybook. Единственный источник команд — корневой `package.json`; Bash-скрипт лишь вызывает их. Операции не меняют staging и не создают коммиты.

Различия CI: Ubuntu 24.04, установка системных библиотек Chromium, загрузка диагностических артефактов и публикация Pages после успешной проверки `main`. GitHub secrets и серверные сервисы не требуются. Включение обязательного check в ruleset — отдельная настройка владельца репозитория.

## Ручная проверка

1. В новом браузерном профиле открыть список: отображается пустое состояние.
2. Создать проект с корректным OpenAPI, отредактировать, обновить страницу и удалить с подтверждением.
3. Открыть пример; построить граф и дождаться завершения. Проверить поиск и управление узлами клавиатурой.
4. Исключить страницу, убедиться в пересчёте плана, вернуть страницу. Снять все профили: запуск недоступен.
5. Запустить симуляцию. Проверить промежуточные результаты, матрицу перед предпросмотром, фильтры, экспорт и историю после reload.
6. Повторить запуск и отменить. Обновление страницы во время выполнения не оставляет приложение занятым.
7. В DevTools → Network убедиться, что нет REST-запросов или обращений к адресу проекта. Загрузка JS/CSS/шрифтов и Vite HMR при разработке нормальна.
8. Повторить основные действия при ширине 390 px; открыть и закрыть навигацию, проверить отсутствие горизонтального скролла всей страницы. Таблицы и граф имеют собственный скролл.
